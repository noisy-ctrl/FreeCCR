# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

FreeCCR is a cross-platform desktop application for batch image preview, selection, negative film conversion, and color correction. It supports RAW and standard image formats with a PySide6 (Qt) GUI and compiles to a standalone executable via Nuitka.

## Dev Commands

```bash
# Install dependencies
pip install -r requirements.txt

# Generate version file from git tags (required before first run)
python write_version.py

# Run the app in development
python src/main.py

# Run all tests
python tests/run_tests.py

# Run with pytest
pytest tests/ -v
pytest tests/test_pytest_activation.py -v   # specific file

# Build standalone exe (Windows)
./build_exe.bat
# or via Makefile:
make build-windows

# macOS build
make build
make build-compatible    # older macOS targets (MACOSX_DEPLOYMENT_TARGET=10.15)

# Clean build artifacts
make clean
```

**Critical version requirement**: Python 3.11.0 exactly — newer versions fail with Nuitka compilation.

## Architecture

The app follows a layered MVC-like pattern:

```
src/main.py                 → QApplication setup, launches MainWindow
src/ui/main_window.py       → Main window, menus, file dialogs (~380 lines)
src/core/ccr_backend.py     → Singleton managing all loaded CCRImage instances
src/core/ccr_image.py       → Image model — RAW/standard format abstraction
src/core/ccr_processor.py   → Color adjustment math, lens correction, OpenCL GPU kernels
src/widgets/thumbnail_list.py  → Sidebar thumbnails with async loading dialog
src/widgets/image_preview.py   → Central canvas: histogram, zoom, reference frame
src/widgets/sliders_panel.py   → Adjustment controls (White Balance/Tint, tone, saturation, Channel Levels, Channel Balance)
src/activation/activation.py   → License validation (disabled — always returns True)
src/utils/unicode_path_utils.py → Cross-platform Unicode filename handling
```

**CCRBackend** is a global singleton — always access loaded images through it rather than holding direct CCRImage references.

## Key Patterns

**Async image loading**: `ImageLoaderWorker` (QObject subclass) runs in QThread with a `ThreadPoolExecutor` of up to 8 workers. Images are sorted by filename after the parallel load completes. A cancellable progress dialog is shown during batch loads.

**HDR export is a gain map over the untouched SDR picture**: the "JPEG + HDR gain map" format writes the exact pixels the plain JPEG would (the primary) plus a single-channel gain map. The glow follows the FINISHED picture (revision 2 — the first version measured only pre-White-Point data, so WP and Brightness could never grow it): `glow = H·tanh((r²·0.5·H + r·log2(max(over,1)))/H)` with `r` ramping from 0.80 display luma (Rec.709) to white on the finished SDR frame, and `over` the brightest channel recorded by `_apply_working_space_recovery` AFTER every gain incl. White Point but BEFORE the auto-tone shoulder and the clamp — only while a thread-local `ccr_processor.hdr_capture()` is open, so no render signature changed. H = the export's headroom (0.5–3, default 2); `GLOW_KNEE`/`GLOW_EXPAND` in `core/hdr_gainmap.py`. The four export tails open the capture around `apply_adjustments(for_export=True)` and push the map through the same crop/orientation (`hdr_geometry`); `write_export_image` computes the glow on the frame (`glow_map`) BEFORE any border, then `_write_hdr_jpeg` → `encode_gainmap_jpeg` hand-assembles an Ultra HDR file (ISO 21496-1 + Adobe `hdrgm` XMP + MPF, the layout libultrahdr 1.4 writes; tests decode it with libultrahdr via imagecodecs, but writing needs only cv2). Non-windowed bases (reference-frame, positive) get the bright-end term only. The **☀ HDR** toolbar toggle (`ccr_backend.hdr_tint_headroom`, session-only) draws the glow as black-and-white halftone dots (`false_colour.glow_dots_rgba`, density = glow; it was magenta until False colour arrived) as its OWN `QGraphicsPixmapItem`, a child of the picture item (`_refresh_glow_overlay`, end of `apply_transformations`), from the preview render's opacity map (`hdr_alpha` → `_preview_hdr_alpha`), cropped like the displayed preview — never baked into pixels, so scopes, probe, histogram, thumbnails, hi-res tiles and exports never see it. See `spec/hdr-gain-map-export.md`.

**False colour is a display layer, like the HDR dots**: the **False colour** toolbar toggle (a text button; `ImagePreview.set_false_colour`, session-only) shows the classic cinema false-colour bands (purple 0–2.5 %, blue 2.5–4, green 38–42, pink 52–56, yellow 97–99, red 99–100, greyscale elsewhere) on the video luma (Rec.709 on display values) of whatever pixmap is DISPLAYED — computed in `core/false_colour.py`, drawn as its own child `QGraphicsPixmapItem` of the picture item at z 1 (the HDR dots are z 2), cached on the pixmap's `cacheKey`, capped at 4096 px, refreshed at the end of `apply_transformations`; a legend `QLabel` sits bottom-left on the viewport. Neither layer is ever in the picture's pixels, so scopes, probe, histogram and exports never see them. See `spec/false-colour.md`.

**Export JPEGs at quality 90+ are 4:4:4**: every export JPEG (plain, the HDR gain-map JPEG's picture, and the size estimate) takes its encoder settings from `core/jpeg_params.jpeg_params(quality)`, which adds full-resolution colour (no chroma subsampling) at quality ≥ 90; below that OpenCV's 4:2:0 default stays. Keep all three on the helper so the HDR base stays identical to the plain JPEG and the estimate matches. See `spec/jpeg-chroma-444.md`.

**Export border / canvas**: the Export window's Border section (`ExportPlan.canvas`, an `export_canvas.Canvas(width, height, long_edge, colour)`) is threaded exactly like `hdr` down to `write_export_image(canvas=…)`, where `export_canvas.compose` centres the finished (cropped, oriented) frame on the canvas — long edge scaled to `long_edge`, shrunk to fit if it would overflow, never cropped — INSTEAD of the `max_long_side` resize and BEFORE the colour-space step, so the border colour (8-bit sRGB × 257) is converted with the picture. The HDR map is placed the same way and padded with 0, so in a gain-map JPEG the border sits at SDR white and only the frame glows. A monochrome frame keeps its single-channel file only on a neutral border. While the box is ticked the Resize combo is disabled; the linear-merge format disables the whole section (its resize parking now uses `_linear_parked`, not the combo's enabled state). See `spec/export-canvas-border.md`.

**Rotate / flip act on the whole selection**: with more than one thumbnail selected, the toolbar's four orientation controls and `[` / `]` all route through `ImagePreview._change_orientation`, which asks first (`orientation_prompt` builds the box; a flip over a MIXED selection offers *Flip Each* and *Flip the Other N*, otherwise Yes / No; No/Esc cancels everything) and gives each changed frame its own undo snapshot. The two mirror actions are checkable purely as an indicator: their state is always set from the frame on screen by `_sync_mirror_actions` (in `update_preview`, `clear_preview` and after every change), never left to Qt's own click toggle. See `spec/multi-frame-orientation.md`.

**The wheel goes where the pointer is** (`spec/wheel-routing.md`, `ui/wheel_routing.py`, installed in `main.py`): Qt 6 latches a phased scroll sequence onto the widget it began on and only releases it on ScrollEnd; a lost ScrollEnd left every later (phase-less) mouse-wheel notch zooming the picture on a Mac. `WheelRouter` (app event filter) compares Qt's first delivery of each wheel event with the widget under the pointer (from the QWindow event, matched by timestamp) and re-delivers it there with manual propagation when they're unrelated; a phased gesture keeps its own lock until ScrollEnd. Don't remove it because it never fires on Linux: X11 sends no phases. Since upstream 2.2.1 the main window's own event filter is APP-WIDE (Up/Down always switch image, even from a focused slider or text box; drags anywhere in the window load files); `MainWindow.eventFilter` scopes both to widgets whose `window()` is the main window; it is reached through ONE app-level `_AppWideHook` pointed at the newest window (upstream installed each window as an app filter, and with the suite's dozens of live windows every event ran through all of them, which stalled the wheel-routing tests), so dialogs and open combo popups keep their keys and drops. Settings' `_WheelScrollsPage` (2.2.1: the wheel over a combo/spinbox/slider scrolls the page) still works when the router re-delivers the event, as the router's `sendEvent` passes through the widget's own filters (`tests/test_upstream_221_merge.py`).

**Every QThread needs a 16 MB stack**: create them only through `src/utils/qt_threads.py` — subclass `WorkerThread`, or call `new_thread()` instead of a bare `QThread()`. macOS gives a QThread 512 KB by default, and numpy's OpenBLAS overflows that on any `np.linalg.solve`/`inv`, even 2×2 (its parallel LU keeps a per-CPU job table on the stack), which killed Convert All with SIGBUS "Thread stack size exceeded". Linux defaults to 8 MB, so it never shows in development; `tests/test_qthread_stack.py` fails on any QThread created another way, and runs a solve under a 512 KB `RLIMIT_STACK` to mimic a Mac. Python's own threads already get 16 MB on macOS. See `spec/qthread-stack-size.md`.

**Image processing pipeline**: RAW files decoded via rawpy → 16-bit numpy arrays → resized to 1080px max side → `ccr_processor.adjust_image()` applies color corrections. OpenCL GPU acceleration is optional and conditionally compiled. Thumbnails (8-bit) are generated separately from full previews.

**Preview detail is display resolution only** (`spec/preview-detail.md`): Settings → General → Preview → Fast / Balanced / Full replaced the "full resolution at 100% zoom" and "sharp preview" checkboxes. `ccr_backend.set_preview_detail(level)` sets `preview_detail` AND the two flags it subsumes (`sharp_fit_preview`, `full_res_zoom`), so existing code keeps reading those; `preview_caps()` → (fit cap, zoom cap), Balanced = (2000, 6000), applied as a clamp on `want` in `ImagePreview._hires_target_long_side` (the half-size floor in `hires_decode_request` still applies). QSettings `view/preview_detail`, migrated from the two old keys when absent; the old keys are still written.

**Live edits render off the GUI thread, latest wins** (`spec/slider-speed.md`): slider, curve and area-feather changes store their settings and call `SlidersPanel._live_request()`; `widgets/live_render.LiveRenderer` snapshots the image on the GUI thread (`CCRImage.preview_render_snapshot`, deep-copied settings/areas) and renders `render_preview_pixels(snap)` on a `QThread`, one job at a time, collapsing requests that arrive meanwhile into one pending entry per image. `update_thumbnail_and_preview()` is now exactly `render_preview_pixels()` + `_apply_preview_pixels()`, bit-identical to before, under a per-image `render_lock` (weak-keyed, so `CCRImage` stays copyable) — a synchronous render waits for an in-flight live one and bumps `_render_epoch`, which voids the late result. **Do not reintroduce `update_preview` before rendering on a live path**: `ImagePreview.update_preview` reads the cached pixmap and only THEN calls `set_current_idx`, which used to re-render synchronously — that is what left the canvas one tick behind and never showed the last value. `set_current_idx` skips its render (and leaves the settle timer alone) inside `SlidersPanel.live_refresh()`; panel sites that render first use `_show_rendered()` so they render once. The 150 ms debounce (and `sliderReleased`) is the idle SETTLE: it requests a full render if the last one stored was a half-resolution draft. Drafts happen only mid-burst, only when the last full render took > `DRAFT_THRESHOLD_MS` (70), never with dust spots (the preview-scale heal caches its source plan; another resolution would overwrite it); they use the full base's Auto Gain (`auto_gain_override`) and a scaled sharpening radius and are upscaled back to the base size, so overlays/crops map unchanged. Auto Gain is cached per base object (`_cached_auto_gain`, weakref + sparse fingerprint + window flag + crosstalk values; not with dust). A late result never redraws while the canvas is in crop/slice mode (any refresh exits them). OpenCL device default is unchanged; `FREECCR_OPENCL=0` forces numpy, `FREECCR_OPENCL_DEVICE=gpu|cpu|<n>` overrides, `FREECCR_RENDER_TIMING=1` logs each live render, and `tools/bench_render.py` times every engine on the user's machine.

**Negative inversion**: Uses the v0.2.3 method — per-channel linear black/white-point normalisation against the reference crop (1st/99th percentiles), an optical-density mean-equalisation for cast balance, a linear `65535 - v` inversion, then `apply_postinvert_look` (saturation boost + shadow warmth). `ccr_normalize_with_reference` (auto reference frame) and `ccr_normalize_with_bwpoint` (user-sampled clear/dense points) share this path; the resolution-independent replay (`compute_reference_norm_params` → `apply_reference_normalization`, params `p_lo`/`p_hi`/`od_factors`) reproduces it for zoom/slice/export.

> **Parked experiment — density-space inversion** (branch `feature/density-tone-rendering`, do not delete): a physically-faithful Cineon/negadoctor-style inversion in optical-density (log) space (subtract `Dmin` offset, divide by film gamma, recover scene-linear `H = 10^(d/γ)`, then a display render). It was made permanent on `main` for a few releases (PRs #23/#24) but **reverted** here because converted frames came out far too dark (subject near-black, needed ~+50 brightness) with amplified chroma noise in the shadows — the faithful log stretch reveals scan/grain noise that the v0.2.3 affine pre-balance hid. The branch carries the full density pipeline + a brightness-norm/simple-gamma tone stage and env knobs (`FREECCR_DENSITY_*`); revisit if attempting a faithful inversion again. Note: a per-channel *multiply* before the log is a clean density offset (no tone-dependent color shift); a per-channel *black-subtract*-before-log (v0.2.3's stretch) warps each channel differently and is what trades faithfulness for the brighter, lower-noise look.

**Channel Levels is the FIRST adjustment stage**: on a windowed working-space base it runs inside `_apply_working_space_recovery` — ahead of White Balance, White Point and Gain, and **before the window clamp** — so it sees un-clamped display values that may sit below 0 or above 1. That is what makes a per-channel *shift* translate the whole histogram (sub-black film base rises into view; content pushed out the bottom lands in the shadow margin) instead of merely adding to what is already displayed. Consequences for anyone touching this: the stage order inside it is **Input Gain → per-channel Shift/Gain/Blackpoint → Master Shift** (Master is its own stage, *not* summed into the per-channel values as it once was), and **Master Gain is no longer part of it** — it is applied AFTER Channel Balance (`_master_gain_divisor`, `include_master_gain=False`), because an exposure control in front of a tone-weighted node made a gain change move the colour; Auto Gain rides that same parameter and moves with it (see `spec/master-gain-after-balance.md`); `adjust_image`/`adjust_image_opencl` **zero** the twelve `ch_*` params after the numpy pre-stage so the kernel can't re-apply them (this is why GPU/CPU parity is free on the windowed path); the kernel's own copy of the block runs only for non-windowed bases and clamps. `_default_slope_invert` deliberately no longer floors density at 0 — without that sub-base data the film base and a true image shadow are numerically identical and no per-channel control can separate them. `WS_LO` is 1.0 (not 0.5) to give that data room; the window *width* is unchanged, so display precision and highlight headroom are effectively untouched. See `spec/channel-levels-pre-clamp.md`.

**Channel Balance is the tone-weighted colour control, White Balance the flat one**: the three `balance_r/g/b` sliders are one anchored **curve node per channel** — `(0,0), (0.1875, y), (1,1)` through the Curves editor's own `_monotone_cubic`, so a move is exactly what dragging that node by hand gives. The node moves in **gamma**, not by a linear offset: `y = BALANCE_NODE_X ** (1/2**stops)` with `stops = (slider/100)·BALANCE_MAX_STOPS`. That is deliberate — a linear offset must stay below `BALANCE_NODE_X` or it crosses the pinned `(0,0)` and breaks monotonicity, and that cap is what stopped a heavily cast frame being correctable at the slider ends; a gamma move approaches 0 and 1 asymptotically, so **no endpoint invariant exists to violate**. Peak deviation at ±100 is about +0.40/−0.26. `BALANCE_NODE_X` is **3/16**, between 1/8 and 1/4: at 1/8 the curve bit too hard in the deep shadows (a full +100 moved x=0.05 by +0.167 vs +0.111 at 3/16) while the peak deviation is essentially the same, so 3/16 keeps the reach and drops the harshness. The asymmetry is inherent: a node at x=3/16 can rise most of the way to 1 but can never fall further than 3/16, so the downward side saturates near −0.26 and raising `BALANCE_MAX_STOPS` buys upward range only. Why a curve and not a gain: **Temperature/Tint is a contrast control on a density base.** WB is a flat per-channel *multiply* on the de-windowed display value, and on a `bw`/no-anchor conversion that value IS optical density — multiplying a log value is a per-channel gamma change, not a colour shift. It only behaves as real WB where the base is not density — `ref` conversions and Positive mode — which is exactly why both controls exist: Balance shipped as its REPLACEMENT in #130 and was then demoted to a collapsible under Channel Levels (default collapsed, with Master Gain below it, matching the render order), with Temperature/Tint restored above Brightness, the WB Picker/AWB driving them again, and the U/I/O + J/K/L nudge keys made opt-in (`ccr_backend.balance_hotkeys`, Settings → General → Keyboard, default off — gated by `QShortcut.setEnabled` so the six letters are not consumed at all while off). See `spec/white-balance-restore.md`. The tone-*uniform* density controls already exist (Channel Levels **Shift** = density offset, **Gain** = slope); what was missing is the tone-*weighted* one, which is what corrects **crossover** (dye layers whose casts diverge between shadows and highlights). The stage runs inside `_apply_working_space_recovery`, un-clamped, **after** Channel Levels and **before** White Balance, because on a windowed base much of the data still sits outside `[0,1]` where the node is identity, so Levels must place the histogram in the window first. Values outside `[0,1]` **pass through unchanged** (both endpoints are pinned, so identity-outside is continuous), which is what preserves the shadow margin and highlight headroom. `balance_*` are appended at the very END of the `adjust_image`/`adjust_image_opencl`/`_apply_working_space_recovery` signatures — those are called positionally in tests, so a mid-signature insert would shift every later argument. The non-windowed path runs the *same* float function on `img/65535`; on the OpenCL path Balance is consumed in numpy, and when Channel Levels is also active Levels is consumed in numpy too (the kernel would otherwise run it *after* Balance and reverse the order). `temperature`/`tint` never lost their pipeline stage, so restoring their sliders was pure UI plumbing and every catalog ever written renders unchanged. The neutral solve (WB Picker / AWB) is a **closed loop on the real render**, `CCRImage._solve_neutral_knob` + `solve_neutral_wb` (what the UI drives, returning temperature/tint) or `solve_neutral_balance` (the Balance trio, retained + tested but no longer wired to a button): it renders the sampled AREA through the actual pipeline, measures the mean that came out, corrects, repeats. There is deliberately **no analytic inverse** of any colour stage any more — inverting it means modelling every other stage (Channel Levels, the hidden Auto Gain offset, gamma, curves, Cineon), three such models shipped and each was wrong in some configuration; do not reintroduce one. WB is two knobs with independent objectives (`R−B` for temperature, `G−(R+B)/2` for tint, temperature first) and converges in one pass. For Balance, red is the anchor and never moves; each pass solves blue then green onto the mean of the other two MEASURED channels (R=134,G=120 → B=127), which with red pinned halves the gap per pass and converges to grey. Per-channel bisection on the measured output; the best-so-far result is kept so more passes never regress. `apply_adjustments` gained `auto_gain_override` (Auto Gain must be measured from the full base — a patch has no highlights) and `skip_dust` (spatial, meaningless on a detached patch); area layers are suppressed via `areas_override=[]`. A channel with no response (B&W profile) is left at 0 rather than pegged. **AWB** uses the same loop as a whole-frame regression: it downscales the frame to 256px (a downscale, not scattered pixels, because `gray_edge` needs neighbours), renders it each iteration and drives the estimator's reading of the RENDER to grey. Anything passed as `combine` **must report in the render's 0–65535 scale** and may be monotone DECREASING — `estimate_neutral_rgb` returns normalised [0,1], and feeding that in unscaled made the flat-response guard fire on every channel; `gray_edge` reports gradient energy, which falls as a channel is lifted. Both silently made the AWB button do nothing, so the guard and tolerance are now relative and the bisection detects direction from its endpoint probes. `gray_edge` is additionally used as a pixel SELECTOR (`gray_edge_pixel_mask`, fixed on the base) rather than a value statistic, since gradient energy cannot be driven to grey. See `spec/channel-balance.md` and `spec/white-balance-restore.md`.

**Cineon Log → Workspace is a DECODE, not a display transform**: the `cineon_log` checkbox runs **between Channel Levels and Channel Balance** (inside `_apply_working_space_recovery` on a windowed base, in the single normalised pass on a non-windowed one, in the numpy pre-stage on OpenCL) and encodes into the **working space's curve (sRGB)** — not at the end of the chain into Rec.709 γ 2.2, which is where it shipped. Both follow from what the stage is for: it is the BOUNDARY between the two domains. Above it, Channel Levels grades in log (a per-channel shift there is a density offset); below it, everything is built for display-referred data — Balance's node sits at a fixed *display* value, then Master Gain, White Balance's flat multiply, the contrast S-curve pivoting on 0.5, saturation's luma weighting, the Curves editor's 0–255 domain — and all of them were grading log values instead. The transform **never applied a matrix** — it is transfer-function-only, the primaries are already the workspace's, so "→ Rec.709" only ever described the gamma. It is **floored at 0 but not ceilinged** (the sRGB power segment is undefined below 0; the headroom above white has to survive for the White Point recovery just below it), which is why the old cached uint16 LUT is gone and the math runs in float32. Consequence worth knowing: the decode turns a cast from a log OFFSET into a linear RATIO, and a cast that is mild in log can exceed WB's 1.4/0.6 = 2.33:1 span (and even peg the Balance node at 100) — a strong cast belongs in Channel Levels ABOVE the decode, where a per-channel shift is a density offset. Auto Gain also still MEASURES the log base while riding a Master Gain that now scales the decoded image, so its highlight placement is approximate with the flag on. `cineon_log` is appended at the END of the `adjust_image`/`adjust_image_opencl`/`_apply_working_space_recovery` signatures for the same positional reason as `balance_*`, and the OpenCL numpy pre-stage now runs when Balance is active **or** the flag is set (the kernel would otherwise apply Channel Levels after the decode). Area layers grade the already-decoded base. See `spec/cineon-display-transform.md`.

**Film Look is a fitted decode in Cineon's slot**: `adjustment_settings["look_lut"]` names a `.cube` in the looks library (`<app data>/looks`, beside `camera_profiles`); `CCRImage.apply_adjustments` resolves it (`core/look_lut.resolve_look`, cached on path+mtime) and passes the parsed `LookLUT` as `look_lut`, appended LAST to `adjust_image`/`adjust_image_opencl`/`_apply_working_space_recovery` (positional callers). It runs right after Channel Levels and **instead of** Cineon (one decode at a time), on both the windowed and the normalised non-windowed pass and in the OpenCL numpy pre-stage. With a look set, **Auto Gain, the baked `eb` and the negative `brightness_base = -8` are all suppressed** — they are display-referred adjustments to the *default* render and the look is the render, fitted with every slider at 0; exposure is Master Shift (a density offset) and colour R/G/B Shift/Gain, which is exactly the per-frame parametrisation `tools/fit_look.py` fits and reports (`look_fit.channel_levels_for`). `look_lut` is a GLOBAL flag carrying a VALUE: the re-attach/sync/copy paths copy `adjustment_settings[flag]` rather than `True`. The fitter (`core/look_fit.py`, numpy+OpenCV only — SciPy breaks against the numpy<2 pin) decodes through the app's own merge, takes the black point per frame from the brightest rebate band, registers to the lab scan with SIFT+RANSAC over four flips, and fits `lab ≈ F(d·(1+g_k)+o_k)` in TWO stages (offsets first, then a ridge-damped per-frame contrast — a joint start from zero stalls in a curve-vs-gain trade-off). See `spec/film-look-lut.md`.

**Highlights ⅃ / Shadows L / Contrast L ⅃ are measured tone tables** (labels; keys `highlights_x`/`shadows_x`/`punch_x`) (`spec/x-tone-tools.md`, `core/x_tones.py`, data `core/x_tones.npz` built by `tools/fit_x_tones.py` from graded HALD images at 0 / ±50 / ±100): per tool and sign a 33³ grid of the change on FreeCCR display values, stored as the quadratic through 0, 50, 100 (`A t + B t²`, t = |v|/100), with the measured black..white mapped onto FreeCCR's (so the grey axis is all measured) and colours outside the measured render filled by harmonic extension. A render evaluates the whole chain (Highlights ⅃ + Shadows L read at the same input and added, then Contrast L ⅃; Range = a per-channel bias remap of where the change is read; Keep = a luma smoothstep fade to the pinned end) at the grid's nodes once per setting (`_composite`, cached) and then does ONE trilinear lookup per pixel, in chunks; `_unfolded` pulls a far Range towards the middle / widens a Keep just enough that the grey axis never turns back (default options are left alone). Runs right after Highlights/Shadows; `highlights_x`/`shadows_x`/`punch_x`/`xtone_shape` are appended LAST to `adjust_image`/`adjust_image_opencl`; on OpenCL the pre-H/S stages + `_apply_highlights_shadows` + the tools run in numpy and are zeroed for the kernel (exact parity). Shown with Highlights ⅃ under Highlights, Shadows L under Shadows, Contrast L ⅃ under Contrast (layout order only, moved from under Black Point 2026-10-24; created after Black Point, which is what `ADJUSTMENT_KEYS` zips with); the labels' L / ⅃ marks are drawn in RED (`x_tone_popup.marked_html`, rich text; the plain name is the label's `accessibleName`) and were swapped on 2026-10-23 (Highlights ⅃, Shadows L — they had been the wrong way round); right-click a label (`widgets/x_tone_popup.py`) for `adjustment_settings["xtone_shape"]` (None when default), plumbed like `organics_shape` (attach on rebuild, load, one undo per popup, Tone sync group, paste row, copy). The data file must ship with builds (`--include-data-files=src/core/x_tones.npz=core/x_tones.npz` in all three build scripts). **Highlights/Shadows are back to the plain anchored bumps** (`_apply_highlights_shadows`, shared with the OpenCL pre-stage): their right-click range/keep options were removed on 2026-10-22 and an old `tone_shape` is ignored (kept in the signatures for positional callers).

**Auto black point measures the film base per frame**: `core/auto_black_point.find_rebate` reads the RAW preview (the same data a manual Set Black Point samples, so values are interchangeable), follows the brightest band along each edge in 10 segments (film sits slightly askew; a straight band drifts off a ~10 px strip), and accepts a band only if it is even (segment IQR < 6 %), unclipped (< 25 % of pixels at the frame's ceiling), a step brighter than the image inside it, and not darker than the interior's p99. ≥ 2 agreeing edges → high (brightest of the group: fall-off only darkens), one → medium, none → low. A pick is "clipped" (low, "expose that channel shorter") only on a PILE at the ceiling — ≥ 2 % of its own pixels at ≥ 0.999 × the frame's max in a channel (`PILE_SHARE`) — or within 10 % of the ceiling in a channel another edge clipped; merely being within 2 % of the frame's brightest pixel is NOT clipping (revision 2026-10-24: on quiet scans like trichrome merges the clear film IS the frame's max, that rule failed every frame and Convert fell back to a stale sampled black point → near-black conversions). Reason channel names follow the array order (B G R). `resolve_auto_black_point(result, consensus, raw)` lets a frame's own low-confidence border win (source `"own"`) over a sampled/roll fallback that > 1 % of its picture is clearer than (`clearer_share`). `roll_check` downgrades a frame that jumps against the roll in EVERY channel (light round the film) but accepts a one-channel shift (a drifting LED — the case that motivated this). `ccr_backend.auto_black_point` is always on (the tickbox was removed, `spec/auto-black-point-always.md`): Convert Current/All use each frame's base (fallback: sampled black point → roll consensus → the fixed-constant density invert, confirmed first on Convert Current and counted as `unanchored` in Convert All's summary), scale a sampled white point by the per-channel base ratio, and record `conversion_inputs["auto_bp"]`; the base goes into `["bw"]` like a sampled one, so no replay site changes. The batch detects every frame first (one reload), then converts. See `spec/auto-black-point.md`.

**The finishing tools run on the GPU** (`spec/gpu-finishing-tools.md`, `core/finish_gpu.py`): on an OpenCL GPU device, `adjust_image_opencl` runs Golden Highlights → Shadow Neutralise → Shadow Lift → Glow on the main kernel's own buffer (`_finish_on_gpu`, inside the GPU lock), so the picture leaves the GPU once; otherwise (CPU OpenCL device, `FREECCR_GPU_FINISH=0`, or after one failure, `_gpu_finish_broken`) the numpy calls below it run as before. `FREECCR_GPU_FINISH=1` forces it on any OpenCL device (the tests do, on pocl). The numpy modules stay the REFERENCE: every constant and option is read from them and each kernel is the same maths in the same order — the OKLab (matrices substituted as exact float32 literals), the guided filters (box filter = `oklab._box`: normalised, `BORDER_REFLECT`, a sliding window over runs of 32 so its cost doesn't grow with the radius), `finish_matte`, `fit_move`'s 12-step bisection, and for Glow OpenCV's own `INTER_AREA` / `INTER_LINEAR` tables and Gaussian kernels built on the host (`area_table`, `linear_table_x/_y`, `gaussian_kernel`: OpenCV's horizontal bilinear pass resets the weight at the edge, its vertical pass only clamps the row). Pixels no tool moved are written back from a `moved` mask only, so they are bit-for-bit the main kernel's output; the main buffer is only written in the last kernel, so a failure part-way falls back cleanly. **Change a tool's maths in its numpy module AND in `finish_gpu.py`**; `tests/test_finish_gpu.py` holds them to ≤ 3 codes (measured ≤ 0.5) per tool, options and sizes, plus the building blocks against cv2. pyopencl's own reductions need Mako (not installed), so `FinishGPU.max` is its own kernel. Speed: on pocl (CPU OpenCL) it is ~2–3× SLOWER than numpy (transcendentals), which is why "auto" is GPU-only; `tools/bench_finishing.py` times numpy vs GPU on the user's machine.

**Finishing tools must keep the picture's quality (the user's standing requirement, 2026-10-22)**: any stage that changes pixel values (1) is an exact no-op at 0 and returns the pixels it doesn't move bit-for-bit; (2) works in float32 or better inside the stage (the uint16 between stages is the only quantisation); (3) uses only C¹-smooth weights, no hard thresholds (no banding, speckle or posterisation); (4) never reorders tones or colours along a gradient — state and test the peak stretch of any selective move; (5) never clips a channel: shorten the move to fit (`core.oklab.fit_move`, < 1 16-bit code) and never darkens a highlight unless that is the tool's purpose; (6) never lets grain steer it — decide HOW MUCH on `core.oklab.decision_lab` (guided filters at the render's own resolution: never decide on a smaller map and scale it up, that stair-steps along edges at export) and apply per pixel, so colour grain is kept or reduced (a per-pixel colour gate measured 1.3–2.4× grain gain on real scans); (7) is resolution independent (preview == zoom == export) and gives the same picture on CPU and GPU (a finishing tool's GPU twin lives in `core/finish_gpu.py` and is tested against the numpy reference); (8) pins all of this in tests (no-op, identity, a 16-bit-fine ramp stays monotone and smooth, in range, a noisy patch's grain doesn't grow, CPU == GPU). Report measured numbers, not impressions.

**Printer Lights are a front end, not a stage**: the D/C/M/Y pad (`spec/printer-lights.md`; density first, half a point per click, Shift-click one, right-click resets, no step row) only moves the Channel Levels R/G/B/Master Shift sliders, plus a γ−/γ+ column after D that moves the tone Gamma slider in its own direction (+ lifts the midtones, 2 per click, 4 per Shift-click), `PRINTER_POINT_UNITS = 3` per point. Those four sliders are `HalfStepSlider`s (integer position = 2 × value, range ±200 for ±100) so a half point (1.5 units) is exact; `value()`/`setValue()` speak value units and return an int for whole values, so callers and stored settings are unchanged — use `value_range()`/`value_text()` rather than `minimum()`/`str(value)`, and `QSlider.value(self)` for the raw position inside slider classes (0.025 log E × `DEFAULT_DENSITY_SLOPE` 0.8 × `CH_SLIDER_DIV` 150), "+" = more of that colour/density = a NEGATIVE shift. Nothing new is stored, so undo/copy/paste/sync/areas/catalogs and the Film Look (which reads density after Channel Levels) need no changes. Keep the constant in step with the slope and divisor if either ever changes (a test pins it).

**The fitted view renders sharp on high-DPI screens**: the preview `QGraphicsPixmapItem` is `Qt.SmoothTransformation` (the item's mode overrides the view's SmoothPixmapTransform hint — the default Fast mode drew enlarged previews nearest-neighbour), and with `ccr_backend.sharp_fit_preview` (Settings → Zoom, `view/sharp_fit`, default on) `_zoomed_in_enough` also fires at the fitted view when view scale × devicePixelRatio > 1.15 and the source out-resolves the preview; `_hires_target_long_side` then asks for exactly `zoom% × source × DPR` pixels via `decide(want, want)` — skipping the 4,140/4,500 floor zoom tiles keep. Dust mode keeps the floor. See `spec/sharp-fit-preview.md`.

**The detail render gives way to the user** (`spec/background-yields.md`, `core/ui_activity.py`): the thumbnail list's scroll bar and every frame switch in `update_preview` call `ui_activity.touch()`; `busy()` is true for 0.4 s after. A fitted-view request that needs a fresh decode waits until the UI has been idle `HIRES_QUIET_S` (0.6 s) via `_hires_defer_timer` (zoom, crop-zoom and dust requests start at once); `HiResDetailWorker.checkpoint` is bound to `load_progress` during the decode and called before the adjustments, sleeping while busy and raising `load_progress.Interrupted` when interruption was requested; a frame switch interrupts every worker for another image (`_stop_other_hires`); `_on_hires_ready` holds a result while busy (`_hires_land_timer`). `Interrupted` is a `BaseException` on purpose: the RAW decode's `except Exception` would otherwise log it as a failed read and set `last_read_error`. A single RAW decode and the OpenCL pass can't be paused mid-way. `tests/conftest.py` resets the clock before every test.

**Master Gain is the app's only gain slider, and it runs after Channel Balance**: the old general-adjustments "Gain" was the same math at a different scale, so it was removed — `"exposure"` is no longer in `ADJUSTMENT_KEYS` or the `tone` sync group. Master Gain is the LAST row inside the Channel Levels collapsible (below Film Look, captioned "applied after Channel Balance"; it folds away with the section — the user's request, 2026-10-30, so the panel no longer reads in render order there) while its `create_slider()` call stays third among the channel sliders, so the positional `ADJUSTMENT_KEYS` zip is unaffected. **Auto Gain rides `ch_master_gain`** (`v = CH_SLIDER_DIV·(1 − 1/g)`, `AG_GMIN/GMAX` = the slider's exact endpoints), so it lands wherever Master Gain lands — now after Channel Balance, which is what makes a Balance correction exposure-independent. On non-windowed bases Levels → Balance → Master Gain run as ONE normalised pass with a single closing clamp: moving that clamp into the middle would change a negative gain's result. The `exposure` *parameter* still exists and is not dead — it carries the legacy baked auto-exposure `eb` (default-slope mode when Auto Gain is off) and area-layer settings; it just has no slider. `eb` was deliberately left on it: `eb` is computed in `50·log2(g)` units but consumed by the `/300` curve, a pre-existing mismatch, and moving it would change conversions without fixing that.

**The toolbar Convert asks Convert Current / Convert All / Cancel** (`spec/convert-button-choice.md`): `ImagePreview._ask_convert_scope` (the test seam) → `convert_ccr` dispatches — Current: a frame with a reference frame drawn converts from it (`_convert_current_by_reference`, the old toolbar behaviour), otherwise the panel's `_on_convert_current_bwpoint`; All: the panel's `_on_convert_all_bwpoint(confirmed=True)` (skips its own "Convert all N images?" question; the button connects through a lambda so `clicked`'s bool can't land in `confirmed`).

**Converting with no anchors is allowed**: with neither a black point nor a reference frame, Convert runs a **fixed-constant density inversion** — `d = −log10(16·p) + 1.0` in log space, `_unanchored_density_invert` — and the user grades it with Channel Levels, which on that base is working in the same density space the black-point-only conversion produces. The `16` and `+1.0` are fixed (a base near half scale lands at ~Cineon black), so nothing is measured off the frame. Log, not linear, is the point: a Channel Levels *shift* on this base is a density offset, i.e. a clean per-channel multiply in linear light, where a linear inversion would make the same slider an additive lift. The negative decode is already linear Adobe RGB (`gamma=(1,1)`, `output_color=Adobe`), so the log is taken on genuinely linear data. Pair it with the **Cineon Log → Workspace** checkbox to decode out of log — without it the result looks flat by design. Crucially this is **not** a new `conversion_inputs` mode — it is the existing `mode: "bw"` recipe with `bw: (None, None)`, which is what it actually is (the B/W-point pipeline with zero points sampled). That keeps ~10 replay/dispatch sites working untouched, since they all hand `ci["bw"]` straight back to the converter; only `apply_bwpoint_normalization` / `ccr_normalize_with_bwpoint` and the catalog's `_ci_to_json`/`_ci_from_json` (which would `list(None)`) needed None-awareness. No black point also means no sprocket mask and no film-stock slopes — both are anchor-relative and are skipped. The UI confirms first via `_confirm_no_anchor_convert`, suppressible with Settings → General → Conversion (`convert/warn_no_anchor`, default on). See `spec/no-anchor-convert.md`.

**Auto white point makes each frame's brightest area white, guarded by the roll**: `core/auto_white_point.py`. With no sampled White Point and no film stock (`ccr_backend.uses_auto_white_point()`, Settings `convert/auto_white_point`, default on), Convert measures each frame's `Dmax` = per-channel median density (above that frame's resolved black point) of the pixels whose channel-mean density is in the 99.0–99.8th percentile of the picture area (crop → `auto_crop_last` → a fresh `detect_frame_crop` → middle 80 %; a centre-only area picks up holder on 35 mm), and converts two-point with `white = base / 10^Dmax_used`. `Dmax_used` keeps the frame's own level but not all of its colour: its ratio is compared with the median ratio of the OTHER frames (≥ 3; Convert All leave-one-out, Convert Current from `conversion_inputs["auto_wp"]["dmax"]` or a cached quick measure of unconverted frames with a known crop), and the difference split into temperature (R−B) and tint (G vs R+B): tint is removed up to 0.15, temperature only up to 0.06 against the roll (a sunset or blue sky is the scene), or warm 0.06 / cool 0.20 against equal channels when there is no roll. Unguarded per-frame neutralising turned sunsets blue; the roll alone left per-frame casts. Recorded in `conversion_inputs["auto_wp"]`; the white goes in `["bw"]`, so replay is untouched. The after-conversion AWB (`maybe_auto_awb`, Settings "Auto white balance after conversion") skips any frame converted with a white point (`["bw"][1]` set) and clears a Temperature/Tint pair it wrote earlier (`img.awb_auto`, in the catalog) if still untouched; see `spec/auto-white-balance.md` §10. See `spec/auto-white-point.md`.

**The white point is chosen per frame, and the auto one is the brightest NEAR-GREY area**: `spec/white-point-choice.md`. `measure_highlights` averages the picture's density into blocks (~1/60 of the short side) and keeps the brightest 10 % that are even inside; `pick_neutral` takes the quarter of those closest to the roll's neutral (within 0.10), which decides *which* area is white (the stone, not the foliage beside it); the roll guard then still caps what is removed (warm/cool 0.06, green/magenta 0.15 — an unguarded pick cooled a sunset whose palest sky is still warm) and the level stays the brightest area's. No near-grey area or no roll → the old guarded brightest area. The roll's neutral is the median of the other frames' recorded near-grey colour (else brightest area); a two-pass "refined" neutral was tried and dropped (on a sky-heavy roll it re-picks sky). Each frame has `img.wp_choice` (None = Settings default: "frame" if Auto white point else "off"; "roll", "off", "sampled") plus `img.wp_sample`/`wp_sample_rect`, all in the catalog; `CCRBackend.resolve_white_point(img, black, hl, reference_fn)` is the one place that turns a choice into a white point (a film stock beats frame/roll, not sampled; a roll-wide `white_point_bgr` set from code still beats everything, as before). Set White Point no longer sets the roll-wide white point — it stores the sample on the current frame and converts it (`SlidersPanel.on_white_point_sampled`), and `_restore_bwpoint` drops the old persisted `convert/white_point_bgr`. The panel's White Point combo + Show (`_flash_wp_areas` → `ImagePreview.flash_areas`) sit under Film Stock; changing the combo re-converts a converted frame.

**Auto tone is a per-frame toe/shoulder measured at conversion**: `core/auto_tone.py`, `conversion_inputs["auto_tone"]` (+ `["picture"]`, the picture rect it was measured in), applied in `_apply_working_space_recovery` after every gain and right before the window clamp (`auto_tone=` appended last to `adjust_image`/`adjust_image_opencl`/the recovery, so OpenCL gets it via the shared numpy pre-stage). Three optional parts, each off unless the frame needs it: `lift` (picture content below black, i.e. clearer than the rebate-measured base because of light fall-off or a roll fallback base, is offset back to black, ≤ 0.15), `toe` (slope at black 1 + toe when > 3 % of the picture is under 0.09 — ~12/255 after the negative look's x^1.3 brightness baseline), `knee/top/sigma` (an exponential shoulder, slope 1 at the knee, `top` → white, strength scaled by the share above white, top capped at 1.3 so lamps clip rather than flatten the frame). `ccr_backend.auto_tone` (Settings `adjust/auto_tone`, default on) only gates the render; frames keep their params. Measured in Convert Current/All and after the density reprocess; slices inherit the parent's. See `spec/auto-tone.md`.

**Camera profiles own their white balance**: the profiled RAW decode is deliberately unbalanced (`use_camera_wb=False`, `output_color=raw`), so `raw.camera_whitebalance` reflects only the camera's WB *setting* — on auto-WB it drifts per frame and used to drift colour with it. A profile generated by the IT8 wizard now records the camera-native neutral of the chart shot it was fit from (`AsShotNeutral` in a `.dcp`, the private `CCRn` tag in an `.icc`), and `color_management.resolve_wb_gains()` lets that neutral **override** the frame's metadata at apply time — one fixed copy-stand setup ⇒ one fixed WB across a roll. Profiles without a baked neutral (imported third-party DCPs, and anything generated before this) fall back to the per-frame metadata. See `spec/camera-profile-calibration-wb.md`.

**Trichrome captures are their own device space**: in a 3-way merge each channel's sensitivity is the sensor's response times *its own* light, and the channel balance comes from three independent exposures — so a white-light camera profile does not describe it. The IT8 wizard can therefore take a **triplet** as its target (`it8_profile.decode_target_merged` sets `is_merged`/`merge_sources` on a bare `CCRImage`, so `read_image` merges it and everything downstream treats it as one raw), and `_read_merged` applies the active DCP/ICC in the same pipeline position as the RAW branch, with `as_shot_wb=None` (no source frame's metadata describes a merge — the profile's baked neutral does). Profiles record which space they describe (`AsShotNeutral`-style private tags: DCP 52525, ICC `CCRk`) and a mismatch logs once. See `spec/trichrome-camera-profile.md`.

**Hot Folder Tether is the watch-folder tethering** (renamed 2026-10-24 from "Tethering"): File → **Hot Folder Tether…** / **Stop Hot Folder Tether**, banner "Hot folder tether: “folder” · N captured". It watches a folder the camera's own tether app saves into. Code identifiers stay `tether_*`. See `spec/camera-tethering.md`. Starting it with images open asks **Add to Them / Start Blank / Cancel** (`_tether_start_choice`, the test seam; Start Blank = `_close_session_for_tether`: save, `ccr_backend.clear()`, reload the list), after the folder is chosen and before "Import Existing Files?" (`spec/tether-start-choice.md`). **The roll black point prompt waits for a LIT capture** (`spec/tether-black-point.md`, `core/lead_frame.py`): the worker sets `img.lit_level` (99.5th percentile of the brightest channel of the unconverted `resized_raw`, share of full scale) before converting, and `_on_capture` only takes a frame with `is_lit` (≥ `LIT_MIN` 0.03; None = lit) as the lead — a dark one (light off) gets a hint and the next is checked. `MainWindow.start_roll_black_point(img=None)` (the banner's **Black Point…**, the Live Capture Monitor's **Set Black Point…** under Shoot, and the prompt) picks `img` / the newest lit capture / the frame on screen, brings the main window to the front and enters black-point sampling.

**File → Live Capture Monitor is a separate window for camera scanning** (`spec/live-capture-monitor.md`, `widgets/live_monitor.py`): the camera's live HDMI view (OpenCV on `core.live_feed.LiveFeed`, a `WorkerThread` doing ONE blocking read per frame and leaving only the newest `FrameResult` for the GUI: never queue frames), the Scanlight over USB serial (`core.light_link.LightLink` is the only code touching the port, on its own thread; `LightClient` is the GUI's handle), presets, shots and the trichrome sequence (`core.capture_sequence`, a timer state machine with injectable clock/light). Its behaviour reference was a separate capture app known to be buggy: re-derive, don't copy (§10 of the spec lists its faults). Everything placed on the picture is in SENSOR FRACTIONS mapped through the rendered frame's `Geometry`; the picture is drawn at device pixels. Closing turns the light OFF and releases the camera and port; opening asks about Hot Folder Tether. Keys (1–4, S, Esc, F) are `Qt.WindowShortcut` on the monitor only. Settings live in QSettings `live/*` (FreeCCR's scope). No focus peaking (the user removed it; Edge amplify, luma-only, replaces it). Idle (`live/idle_minutes`, default 5) turns the Scanlight OFF, not dimmed, and covers the whole control panel with a Wake overlay (`wake_overlay`); only **Wake** restores the levels (`_sleeping`): use still counts towards the idle time but never wakes it, and solo keys / Shoot do nothing meanwhile (spec §7.5). The Negative preview is two/three-point levels in the feed's encoded values (a density model measured 3–4× noisier on 8 bits) and never reaches the conversion; no camera profile or Film Look is applied to the feed. Name the light "Scanlight"; never its maker, nor the capture app the monitor was modelled on (open-source tools and libraries may be named; closed-source software and brands are never emulated and named). `pyserial` is optional at run time; macOS camera access needs the Info.plist usage text, the camera entitlement and Qt's `permissions` plugins in builds. OpenCV can't ask for camera permission off the main thread (`OPENCV_AVFOUNDATION_SKIP_AUTH=1`, Qt's `QCameraPermission` first).

**USB cameras are a Live Capture Monitor route** (`spec/capture-routes.md`, `core/camera_backends.py`, `core/usb_camera.py`): a camera on its own USB cable gives the monitor its live view, its shutter and its files. Two open-source backends: libgphoto2 through the optional `gphoto2` package (macOS 14+/Linux wheels; not in requirements.txt as a hard requirement) and, on Windows, digiCamControl's web server on `127.0.0.1:5513` (a separate app the user installs; its session folder is pointed at the hot folder and put back on close). `UsbCamera` (a `WorkerThread`) is the ONLY code touching the camera; `LiveFeed.open_camera` takes an OpenCV index or a `"usb:<backend>:<id>"` key dispatched to `feed.sources["usb"]` (`UsbCamera.frame_source`), so the picture tools are unchanged. Files ALWAYS arrive through Hot Folder Tether: libgphoto2 files are downloaded into its folder as `.part` then renamed (RAW kept over a same-name JPEG, `_1` on a name clash), so triplets, the light check and Needs attention are untouched; shooting over USB asks to turn the hot folder on. The Shutter row (Capture) picks Scanlight or the open USB camera; with USB the sequence is event-driven (`CaptureSequence.start(shutter=)`: colour → Settle (the Focus field) → fire → `frame_done` on the file, 30 s timeout; Stop never abandons a shot in flight) and a single shot needs no Scanlight. Ports are ranked by USB ID (`port_info_rank`, the Scanlight's RP2040 `0x2E8A` first) because Windows names them `COM5`. **Magic Lantern on the card is warned about** (spec §12): after a libgphoto2 camera opens, `Gphoto2Backend.addons()` lists each card's top level and reports it when both `autoexec.bin` and an `ML` folder are there (`addons_on_card`); `UsbCamera.addons_found` → a warning box once per camera per session (`_addon_notice`, the test seam; `live/warn_addons` turns it off) and a "Magic Lantern on card" badge while it is open. digiCamControl and HDMI can't list the card. The text never names the camera maker. A libgphoto2 camera is labelled with the model it REPORTS once open (`Gphoto2Backend.reported_model`, config `cameramodel` + `manufacturer`), not libgphoto2's table name: Fujifilm reuses USB ids, so a GFX 50S II matches the GFX100 entry. **Never call python-gphoto2's `get_value()` on a text/radio/menu setting**: on one the camera left empty it reads a NULL string and the whole process dies (SIGSEGV, no exception; its NULL check tests the wrong pointer — hit on a GFX 50S II). Read settings through `camera_backends.widget_value`, which calls libgphoto2's own `gp_widget_get_value` via ctypes on the library the package loaded and returns None for an empty one. The Shutter row lists EVERY USB camera found (its entry is the camera's key; the old value "usb" means the open one): picking one opens it as the shutter only, with no live view asked, so a capture device can give the picture. Live view that answers "busy" is retried no more than every `PREVIEW_BUSY_BACKOFF_S` (0.25 s) and given up (`no_preview`, "no live view over USB" message) only after `PREVIEW_GIVE_UP_S` (15 s) busy with no frame EVER: the GFX 50S II refuses live view for a while after shots (a quick-fire test script saw only "busy" and wrongly concluded it had none); on a fresh connection it streams at once, 50 fps in a tight loop. **With live view asked for since the last shot, `fire()` uses libgphoto2's full capture call (`camera.capture`), never the trigger call** (spec §17): libgphoto2 2.5.34's Fujifilm trigger shoots without ending live view and the body refuses it, while its capture routine ends live view first; with no live view the trigger call stays. While live view runs and no shot is on its way, `poll()` checks events only every `LIVE_EVENTS_EVERY_S` (3 s): on a Fujifilm each check writes the priority mode and lists storage, ~0.3 s of picture each (test 5: 3.4 fps checking before every frame, 36 fps once a second, 50 without). A Fujifilm announces its live view frame as a file (`/store_10000002/LIVE0001.JPG`): `is_live_view_file` drops it, and one failed download skips that file instead of declaring the camera lost. After a shot the GFX 50S II's live view stays busy (its LED cycling as if transferring) until the shot is deleted from the camera (test 6: 0.07 s after `file_delete`). **FreeCCR clears a shot from the camera's OWN memory only** (spec §20, the user's decision): after it is saved whole in the hot folder (`_saved_whole`: on-disk size = bytes received = the camera's reported size), never from a memory card (`on_memory_card`: any `DCIM` path part), never with no hot folder or a failed download; a RAW + JPEG pair's JPEG only after its RAW. Don't widen that (e.g. to card files) without asking. A live view that gave frames and then stays busy `LIVE_STALL_S` (5 s) is reported (`live_stalled` → `UsbCamera.live_paused` → a message over the picture). Exposure is read one setting at a time (`get_single_config`): a whole-configuration read is ~150 properties on a Fujifilm and stalls live view. Naming open-source software in the app is fine; closed-source software and brands are not emulated or named.

**Scan type decides how Hot Folder Tether loads files** (`spec/scan-type.md`, `core/scan_type.py`): one app-wide `ccr_backend.scan_type` (`colour` | `trichrome` | `bw`, QSettings `scan/type`, set from the Live Capture Monitor's Capture combo or the tether banner's combo, both through `MainWindow.set_scan_type` → `scan_type_changed`). Trichrome: new RAWs queue in name order (`TripletGrouper`) and each three go to `TetherWatchWorker.process_triplet`, which first checks each frame is lit by its own colour (`light_shares` off the RAW mosaic, `judge_triplet`: channel k largest and ≥ `LIGHT_SHARE_MIN` 0.60 — an estimate), then merges with `create_images_for_merge` exactly like Open. A shot that fails, stalls 30 s, is left over or is waiting at Stop becomes a greyed-out tile in the thumbnail list's "Needs attention" strip (`set_attention`/`attention_action`: Choose Files…, Merge Anyway, Load as Single Frames, Remove) — NOT an entry in `ccr_backend.images`, so list rows stay image indices. B&W and colour: one exposure, whatever light (Shoot uses the light as it is); B&W arrivals get `color_profile = "bw"`. Arrivals record `img.capture_type` (catalog key; None for anything Open loaded). Profile / Film Look mismatch warnings by capture type are deferred.

**Unicode path handling**: Windows non-ASCII filenames require `normalize_unicode_path()` and `validate_unicode_path()` from `src/utils/unicode_path_utils.py`. Always validate paths before passing to image loaders.

**Resource resolution**: `resource_path()` in `image_preview.py` handles both dev and Nuitka-bundled contexts. Nuitka embeds `src/icons/` and `LICENSES/` directories at build time.

**macOS display color management**: Qt raster windows are not color-matched — the Cocoa backing store inherits the NSWindow colorspace (default: the display's own profile), so sRGB-encoded previews render oversaturated on wide-gamut (Display P3) Macs while ICC-tagged exports display correctly. `install_macos_srgb_filter()` in `src/ui/theme.py` tags every top-level NSWindow as sRGB via a ctypes/objc shim so ColorSync matches the whole app to the display profile. Exports embed their ICC profile in `apply_export_colorspace()` (`src/core/color_management.py`) and are unaffected.

**Activation system**: The license verification code in `src/activation/` is present but bypassed — `is_activated()` always returns `True` in this build. Tests in `tests/test_activation_security.py` still validate the HMAC-SHA256 signing logic.

## Workflow

For every major change: create a new branch, make the changes, then open a PR back to `main`.

**New features**: before writing code, author a spec in the `spec/` folder (e.g. `spec/<feature>.md`) covering goals/non-goals, UX/interaction, data model, processing/math, integration points, and a test plan. Refine that spec once more (resolve open questions, tighten integration details) before implementing. Then implement against the refined spec, with tests.
